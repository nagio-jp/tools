# 全画面テストケース作成

静的 HTML のサイトについて、全画面のテストケースを洗い出す。4 つの工程で進め、工程を飛ばしたり 1 回の応答でまとめて済ませたりしない。

- 対象: `$ARGUMENTS`（省略時はカレントディレクトリ）配下の `*.html`。以下 `<対象>` と書く
- 成果物: `<対象>/testcases/` 配下のファイルだけ
- スクリプト: このスキルのベースディレクトリにある `scripts/inventory.mjs` と `scripts/coverage.mjs`（Node.js 標準モジュールのみ、インストール不要）。以下では `<skill>/scripts/...` と書く
- スクリプトの引数は絶対パスで渡す（シェルのカレントディレクトリがずれても壊れないように）

## 絶対に守ること

- **このスキルは洗い出しだけを行う。** nagio などのテスト管理ツールや外部サービスへの登録・送信はしない。MCP のツールが使える環境でも呼ばない。
- **完了かどうかはあなたが判断しない。** coverage.mjs が exit 0 を返したときだけ完了と報告する。
- **スクリプトを書き換えない。** 判定基準が動くと網羅の意味がなくなる。不具合を見つけたら回避したうえで人に報告する。
- **ケースは 1 件ずつ考えて書く。** スクリプトやテンプレートでケースを量産しない。
- 「他の画面も同様」「以下省略」「代表的なものだけ」のように省略しない。
- 1 回の生成で扱うのは 1 画面だけ。複数の画面をまとめて書かない。
- 途中で止まる場合は、どの画面まで終わったかを `<対象>/testcases/progress.md` に書いてから止まる。

## 工程 1: 棚卸し

テスト対象の母数を決める工程。LLM の判断で対象を列挙せず、スクリプトで機械的に抽出する。

1. `node <skill>/scripts/inventory.mjs <対象>` を実行する。`<対象>/testcases/inventory.json` ができる。
   - 抽出する種別: page / form / input / select / radio / checkbox / button（`class="btn"` の a 要素を含む）/ toggle（`data-toggle` で開閉するドロップダウン・折りたたみ・モーダルの起動元）/ action（`href="#"` など、JS で動く a 要素）/ link（サイト内リンク）
   - **共通部品**: 半数以上の画面に同じ形で現れる要素（ナビ・ヘッダー・フッター・共通モーダルなど）は、擬似画面 `_layout` に 1 回だけ載る。各画面からは除かれ、`usesLayout: true` が付く
   - 各要素の ID は `<ファイル>#<種別>:<名前>` の形式
   - 再実行しても、人が付けた `risk` と手動追記した要素は引き継がれる
2. 出力の「HTML ファイル数」と「画面数」が一致することを確認する。
3. スクリプトでは拾えないものを、各画面が読み込む JS を読んで追記する。
   - JS で表示が変わる箇所: 入力エラーやメッセージの表示、`hidden`・`display` の切り替え、`fetch` などによる読み込み（読み込み中・成功・失敗）、グラフ・表の描画、表の検索・並べ替え・ページ送り
   - JS で組み立てるフォームやボタン（HTML に書かれていないもの）
   - 共通部品の JS（ナビの開閉など）は `_layout` に追記する

   追記する形式: `{ "id": "<ファイル>#<種別>:<名前>", "type": "<種別>", "description": "<何が起きるか>", "risk": "normal", "source": "manual" }`。種別は表示の変化なら `state`、操作できる要素なら上の種別から選ぶ。
4. 画面ごとの要素数の表（inventory.mjs の出力）と手動追記の一覧を示し、**ここで止まって人に確認する。**
   - 対象の抜け・不要な対象がないか
   - `_layout` にまとまった要素が妥当か（画面固有のはずの要素が混ざっていないか）
   - 厚くテストしたい画面・要素はどこか（`risk: "high"`）、軽くてよいのはどこか（`risk: "low"`）
   - 指示を受けたら inventory.json の `risk` を更新する。不要と言われた要素は削除せず、工程 3 で `excluded` に理由付きで入れる

## 工程 2: 観点の決め方

要素の種別ごとに、次の観点をケースにする。

| 種別 | 観点 |
|------|------|
| page | 初期表示、URL 直接アクセス、ブラウザの戻る・再読み込み、狭い画面幅での表示 |
| form | 送信先・送信方法が正しいこと、送信後の画面、Enter キーでの送信 |
| input | 正常値、必須の未入力、境界値（minlength・maxlength・min・max の前後）、形式不正（inputType・pattern）、前後の空白・全角文字 |
| select / radio / checkbox | 選択肢ごとの動作、未選択 |
| button | 正常な送信・操作、入力エラー時の送信、連打（二重送信）、送信失敗時の表示 |
| toggle | 開く、閉じる、開閉の繰り返し、外側クリック・Esc で閉じるか、開いた中身の表示 |
| action | 押したときの動作（何も起きない場合はそれが意図どおりか） |
| link | 遷移先が正しいこと、リンク切れがないこと |
| state | 状態ごとの表示、状態の切り替え、読み込み失敗時の表示 |

当てはまらない観点は書かない（例: maxlength の無い入力欄の境界値、静的ページの送信失敗）。除外にも書かなくてよい。coverage.mjs は要素ごとに 1 件以上あるかを見るだけで、観点の網羅までは判定しない。観点の網羅はこの表に沿って、あなたが責任を持つ。

risk による深さの違い:

- `high`: 表の観点をすべて書く。加えて、同じ画面内の入力の組み合わせ（複数項目のエラーが同時に出る場合など）も書く。要素ごと除外することはできない
- `normal`: 表の観点をすべて書く
- `low`: 正常系と表示の確認だけ書く。要素ごと省く場合は `excluded` に理由付きで書く

期待値の書き方:

- 仕様書が無い場合、期待値は「利用者から見てあるべき挙動」で書く。現状の HTML・JS の挙動と食い違うなら、その旨をケースに `"needsReview": "<現状の挙動と、どちらが正しいか判断が要る理由>"` として残す
- 「正しく表示される」のような曖昧な期待値は書かない。画面を見ずに第三者が実施・判定できる具体さで書く

## 工程 3: ケース作成

1. 最初に `_layout` のケースを書く。共通部品の動作はここで 1 回だけ確認する。
2. 続けて各画面を 1 つずつ処理する。`usesLayout: true` の画面では共通部品のケースを繰り返さない。書くのは、その画面にしかない要素と、共通部品の画面ごとの違いだけ（ナビで現在の画面が強調される、初期表示で開いているメニューなど）。違いは、その画面の `page` 要素を covers に入れて書く。
3. 画面数が多ければ画面ごとに Sub Agent を起動してよい。その場合も Sub Agent には担当画面と、工程 2・3 の内容を渡す。
4. 1 画面ごとに `<対象>/testcases/cases/<ファイルの / を __ に置き換えた名前>.json` を書く。形式:

```json
{
  "page": "contact.html",
  "cases": [
    {
      "id": "contact-001",
      "title": "メールアドレス未入力で送信するとエラーが表示される",
      "covers": ["contact.html#input:email", "contact.html#button:送信"],
      "perspective": "必須の未入力",
      "preconditions": "お問い合わせ画面を開いている",
      "steps": ["メールアドレスを空のままにする", "送信ボタンを押す"],
      "expected": "メールアドレス欄にエラーが表示され、送信されない"
    }
  ],
  "excluded": [
    { "element": "contact.html#link:プライバシー->privacy.html", "reason": "risk: low のため" }
  ]
}
```

5. `page` は inventory.json の `file` と同じ表記にする（共通部品は `_layout`）。`covers` と `excluded.element` には inventory.json の ID をそのまま写す（推測で書かない）。
6. 1 画面を書き終えるたびに `<対象>/testcases/progress.md` に完了した画面を追記する。

## 工程 4: 抜けの確認

1. `node <skill>/scripts/coverage.mjs <対象>/testcases` を実行する。
2. exit 1 なら、出力に出た未カバーの要素と形式エラーを工程 3 の手順で直し、もう一度実行する。**exit 0 になるまで繰り返す。**
3. exit 2 は入力ファイルの問題（inventory.json が無い、JSON が壊れているなど）。原因を直してから実行し直す。

## 完了報告

coverage.mjs が exit 0 を返したら、その出力をそのまま貼り、次を添えて報告する。

- risk: high の要素とそのケース数
- excluded の件数と主な理由
- `needsReview` の付いたケースの一覧（現状の挙動とあるべき挙動が食い違うもの。不具合の候補）
- 手動追記した要素の一覧（スクリプトで拾えなかったもの。人の確認を勧める）
