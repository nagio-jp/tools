# 全画面 E2E テストケースの洗い出し

Web アプリ・サイトの全画面について、E2E テストケースを洗い出す。6 つの工程（0〜5）で進め、工程を飛ばしたり 1 回の応答でまとめて済ませたりしない。

- 対象: `$ARGUMENTS` の 1 つ目（省略時はカレントディレクトリ）。以下 `<対象>` と書く。2 つ目に URL があれば、起動中のアプリの URL として使う
- 成果物: `<対象>/testcases/` 配下のファイルだけ
- スクリプト: このスキルのベースディレクトリの `scripts/`。以下では `<skill>/scripts/...` と書く。引数は絶対パスで渡す（シェルのカレントディレクトリがずれても壊れないように）
  - `sources.mjs`・`inventory.mjs`・`routes.mjs`・`coverage.mjs` は Node.js の標準モジュールだけで動く
  - `crawl.mjs` だけ Playwright が要る。対象プロジェクトに Playwright があれば `--project <対象>` で使える。無ければ `cd <skill>/scripts && npm install && npx playwright install chromium` を人に案内する（勝手にインストールしない）

## 絶対に守ること

- **このスキルは洗い出しだけを行う。** nagio などのテスト管理ツールや外部サービスへの登録・送信はしない。MCP のツールが使える環境でも呼ばない。
- **完了かどうかはあなたが判断しない。** coverage.mjs が exit 0 を返したときだけ完了と報告する。
- **スクリプトを書き換えない。** 判定基準が動くと網羅の意味がなくなる。不具合を見つけたら回避したうえで人に報告する。
- **ケースは 1 件ずつ考えて書く。** スクリプトやテンプレートでケースを量産しない。
- **1 回の書き込みで扱うのは 1 画面（1 ファイル）だけ。** 1 回のコマンドやヒアドキュメントで複数画面のファイルを書かない。画面ごとに考えてから書く。
- 「他の画面も同様」「以下省略」「代表的なものだけ」のように省略しない。
- アプリの操作は巡回（crawl.mjs）と、人が許可した setup だけ。データを消す・送る操作を自分で実行しない。
- 途中で止まる場合は、どこまで終わったかを `<対象>/testcases/progress.md` に書いてから止まる。

## 工程 0: 問診（参考にできる資料の確認）

ケースの期待値と網羅の根拠になる資料を、先に人とすり合わせる。

1. `node <skill>/scripts/sources.mjs <対象>` を実行する。`<対象>/testcases/sources.json` に、資料の候補が種類ごとに入る（フロントエンド / バックエンド / API 定義 / DB / 仕様・要件 / 既存のテスト / 認証 / デザイン）。見つからなかった種類も「見つからなかった」と出る。
2. 候補のうち中身を見ないと判断できないもの（README、仕様らしき md、.env.example、form の送信先）は読んで、何が分かるかを一言ずつ添える。
3. 種類ごとの一覧を示し、**1 回の質問で**次をまとめて聞いて止まる。
   - この一覧で合っているか（不要なもの・足りないもの）
   - ほかに参考にできる資料はあるか（リポジトリ外の Notion・Figma・仕様書の URL、既存のテストケース表など）
   - アプリを起動して巡回できるか。できるなら URL（起動中でなければ起動方法）
   - ログインが要るか。要るならテスト用アカウント、または storageState（後述）を用意できるか
   - **バックエンド（送信処理・データ保存・認証）はあるか。** 無い・不明な場合、送信失敗・二重送信・認証エラー・保存後の表示のケースを「あるべき挙動として書く」か「書かない」か
4. 回答を sources.json に反映する。人が足した資料は該当する種類の `found` に `{ "path": "<パスか URL>", "reason": "<何の資料か>", "source": "manual" }` で足す。どの種類にも当てはまらなければ `extra` に足す。回答は `answers` に書く:

```json
"answers": {
  "backend": "exists | none | unknown",
  "backendCases": "write | skip",
  "appUrl": "http://localhost:3000",
  "auth": "不要 / テスト用アカウント: ... / storageState: testcases/auth.json",
  "notes": "その他、人から聞いたこと"
}
```

### 資料の使い方（工程 2〜4 で使う）

- 仕様・要件・デザイン: 期待値の根拠にする。ケースに `basis`（資料のパスと箇所）を書く。根拠があるケースは needsReview にしない
- API 定義・DB スキーマ: 必須・文字数・形式・一意性の制約を補い、境界値・重複登録のケースの根拠にする。作成 → 一覧に出る → 更新 → 削除 のフローを網羅する材料にする
- バックエンドの有無: `answers.backendCases` に従う。`skip` なら送信失敗・二重送信・認証エラーの観点は書かず、除外にも書かなくてよい（coverage.mjs が前提として表示する）
- 既存のテスト: 既にあるケースと重複させない。重複するものは書かず、progress.md に「既存の <ファイル> でカバー」と残す
- 資料が無い種類は、そのぶん期待値が推測になる。完了報告で示す

## 工程 1: 棚卸し

テスト対象の母数を決める工程。LLM の判断で対象を列挙せず、スクリプトで機械的に抽出する。対象の種類で方式を選ぶ。

### A. 静的 HTML（ビルド不要で、.html をそのまま開けば動くもの）

`node <skill>/scripts/inventory.mjs <対象>` を実行する。出力の「HTML ファイル数」と「画面数」が一致することを確認する。

### B. 起動できるアプリ（React・Vue・Next.js など、静的 HTML でも JS で画面が変わるもの）

1. `node <skill>/scripts/routes.mjs <対象>` で、ソースからルートを拾う（Next.js の pages/・app/、Nuxt、SvelteKit、React Router・Vue Router などの path 指定）。`<対象>/testcases/routes.json` ができる。
2. 工程 0 で聞いた URL に対して巡回する:
   `node <skill>/scripts/crawl.mjs --base-url <URL> --out <対象>/testcases [--project <対象>]`
   - リンクをたどり、描画後の画面から操作できる要素を集める。ドロップダウン・タブは 1 つずつ開いて、開いたときだけ現れる要素も集める（開くだけで、送信・削除はしない）
   - `/users/123` のような URL は `/users/:id` として 1 画面にまとめる。一覧の行に並ぶ同じ操作は 1 要素にまとめる（`repeated` に件数）
   - ソースにあるのに巡回で開けなかったルートは、`unreached`（理由付き）として inventory に載る
3. **ログインが要る場合**は、次のどちらかを人に用意してもらい、ログイン前とログイン後の両方を巡回する。
   - storageState: 人に `npx playwright codegen --save-storage=<対象>/testcases/auth.json <URL>` でログインしてもらう
   - setup スクリプト: ログイン手順を書いた ES モジュール（`export default async (page, { baseUrl }) => { ... }`）。テスト用アカウントを人から聞いて、あなたが書いてよい。パスワードはファイルに直書きせず環境変数から読む
   - 実行例: `--session ログイン前 --session ログイン後=<対象>/testcases/auth.json`
4. **データが無いと出ない画面・要素**（空の一覧、行ごとの操作）は、setup スクリプトでデータを作ってから巡回する（`--session データあり=<setup>`）。作る操作は人の了承を得てから。
5. unreached の画面は、実在する URL（`/users/42` など）を人に聞いて `--seed <URL>` を付けて巡回し直すか、理由付きで除外する。

### 共通: 出力の見方と手動追記

- **共通部品**: 半数以上の画面に同じ形で現れる要素は、擬似画面 `_layout` に 1 回だけ載る。各画面には `usesLayout: true` が付く
- **要注意（一部の画面だけ文脈が違う共通部品）**: 出力の「要注意」は、ある画面でだけ form の中にある・押したときの動作が違う要素。不具合の候補なので必ずケースにする
- **既知の UI ライブラリ**: 出力に出た画面（DataTables・Chart.js・地図など）は、ライブラリが描く操作・表示（並べ替え・ページ送り・ツールチップなど）を確認して手動追記する
- 各要素の ID は `<画面>#<種別>:<名前>`。種別: page / form / input / select / radio / checkbox / switch / button / toggle（開閉の起動元）/ tab / menuitem / action（JS で動くリンク・クリックできる要素）/ link（サイト内）/ external（外部リンク）
- 再実行しても、人が付けた `risk` と手動追記した要素は引き継がれる

スクリプトで拾えないものを、画面の JS・ソースを読んで追記する。形式: `{ "id": "<画面>#<種別>:<名前>", "type": "<種別>", "description": "<何が起きるか>", "risk": "normal", "source": "manual" }`。表示の変化（エラー表示・読み込み中・空の状態・グラフの描画など）は `state` にする。

### フロー（_flows）

要素単位では出ない、画面をまたぐ流れを擬似画面 `_flows` に `flow` 要素として登録する。次の観点で、当てはまるものをすべて挙げる。

- 認証: ログイン → ログイン後の画面 → ログアウト、未ログインでの保護画面へのアクセス、パスワード再設定
- データの一生（エンティティごと）: 作成 → 一覧に出る → 詳細 → 更新 → 削除 → 一覧から消える
- 検索・絞り込み・並べ替え・ページ送りの組み合わせと、URL・戻るボタンでの状態の保持
- 複数ステップのフォーム（ウィザード）、確認画面
- 権限による出し分け（ロールごとに見える画面・操作）
- 状態の持ち越し（再読み込み・別タブ・ログアウト後にデータが残るか消えるか）

形式: `{ "id": "_flows#flow:<名前>", "type": "flow", "description": "<画面 A → 画面 B → ...>", "screens": ["<画面>", ...], "risk": "normal", "source": "manual" }`。当てはまるフローが無ければ、`_flows` の `elements` を空にし、`note` に理由を書く（`_flows` 自体が無いと coverage.mjs がエラーにする）。

### 人への確認

要素数の表、要注意、既知のライブラリ、unreached、手動追記の一覧、フローの一覧を示し、**ここで止まって人に確認する。**

- 対象の抜け・不要な対象がないか、`_layout` のまとまり方が妥当か
- 厚くテストしたい画面・要素・フローはどこか（`risk: "high"`）、軽くてよいのはどこか（`risk: "low"`）
- 指示を受けたら inventory.json の `risk` を更新する。不要と言われた要素は削除せず、工程 3 で `excluded` に理由付きで入れる

## 工程 2: 観点の決め方

要素の種別ごとに、次の観点をケースにする。

| 種別 | 観点 |
|------|------|
| page | 初期表示、URL 直接アクセス、ブラウザの戻る・再読み込み、狭い画面幅での表示、（ログインが要る画面）未ログインでのアクセス |
| form | 送信先・送信方法が正しいこと、送信後の画面、Enter キーでの送信 |
| input | 正常値、必須の未入力、境界値（minlength・maxlength・min・max・API / DB の制約の前後）、形式不正（inputType・pattern）、前後の空白・全角文字 |
| select / radio / checkbox / switch | 選択肢ごとの動作、未選択 |
| button | 正常な操作、入力エラー時の送信、連打（二重送信）、送信失敗時の表示 |
| toggle / tab | 開く、閉じる、開閉の繰り返し、外側クリック・Esc で閉じるか、開いた中身の表示 |
| menuitem / action | 押したときの動作（何も起きない場合はそれが意図どおりか） |
| link | 遷移先が正しいこと、リンク切れがないこと |
| external | 遷移先が正しいこと、新しいタブで開くか |
| state | 状態ごとの表示、状態の切り替え、読み込み失敗時の表示 |
| flow | 正常に最後まで進む、途中で戻る・中断する、途中でエラーになる、結果が他の画面に反映される |
| repeated（一覧の行） | 0 件・1 件・多数のとき、行ごとの操作が正しい行に効くこと |

当てはまらない観点は書かない（例: maxlength の無い入力欄の境界値）。送信失敗・二重送信・認証エラーなど、バックエンドが要る観点は工程 0 の `answers.backendCases` に従う（`skip` なら書かない）。coverage.mjs は要素ごとに 1 件以上あるかと観点の記入を見るだけで、観点の網羅までは判定しない。観点の網羅はこの表に沿って、あなたが責任を持つ。

risk による深さ:

- `high`: 表の観点をすべて書く。加えて、同じ画面内の入力の組み合わせ（複数項目のエラーが同時に出る場合など）も書く。要素ごと除外することはできない
- `normal`: 表の観点をすべて書く
- `low`: 正常系と表示の確認だけ書く。要素ごと省く場合は `excluded` に理由付きで書く

期待値の書き方:

- 資料（工程 0）に根拠があれば、それに沿って書き、`basis` に資料のパスと箇所を書く
- 資料が無い場合は「利用者から見てあるべき挙動」で書く。現状の挙動と食い違う、または判断が分かれるなら `needsReview` に理由を書く
- **同じ原因の要確認は findings にまとめる。** 例えば「Login ボタンがただのリンクで、検証も送信も無い」が原因のケースが複数あるなら、ファイルの `findings` に 1 件だけ書き、各ケースからは `finding` で参照する。ケースごとに同じ説明を繰り返さない
- 「正しく表示される」のような曖昧な期待値は書かない。画面を見ずに第三者が実施・判定できる具体さで書く

## 工程 3: ケース作成

1. `_layout` → 各画面 → `_flows` の順に、1 つずつ処理する。
2. `usesLayout: true` の画面では共通部品のケースを繰り返さない。書くのは、その画面にしかない要素と、共通部品の画面ごとの違い（現在地の強調、初期表示で開いているメニュー、要注意に出た文脈の違い）だけ。違いは、その画面の `page` 要素を covers に入れて書く。
3. 画面数が多く、サブエージェントを使える環境なら、画面ごとに任せてよい。その場合もサブエージェントには担当画面と、工程 0 の回答・工程 2・3 の内容を渡す。
4. 1 画面ごとに `<対象>/testcases/cases/<画面の / などを _ に置き換えた名前>.json` を、1 回の書き込みで書く。形式:

```json
{
  "page": "/contact",
  "findings": [
    { "id": "F-contact-no-submit", "summary": "送信ボタンがリンクで、入力の検証も送信も行われない" }
  ],
  "cases": [
    {
      "id": "contact-001",
      "title": "メールアドレス未入力で送信するとエラーが表示される",
      "covers": ["/contact#input:email", "/contact#button:送信"],
      "perspective": "必須の未入力",
      "preconditions": "お問い合わせ画面を開いている",
      "steps": ["メールアドレスを空のままにする", "送信ボタンを押す"],
      "expected": "メールアドレス欄に「必須です」と表示され、送信されない",
      "basis": "docs/spec/contact.md 「入力チェック」",
      "finding": "F-contact-no-submit"
    }
  ],
  "excluded": [
    { "element": "/contact#link:プライバシー->/privacy", "reason": "risk: low のため" }
  ]
}
```

5. `page` は inventory.json の `file` と同じ表記にする（共通部品は `_layout`、フローは `_flows`）。`covers` と `excluded.element` には inventory.json の ID をそのまま写す（推測で書かない）。`perspective` は必須。
6. finding の ID はケースファイルをまたいで一意にする。別の画面の finding を参照してよい。
7. 1 画面を書き終えるたびに `<対象>/testcases/progress.md` に完了した画面を追記する。

## 工程 4: 抜けの確認

1. `node <skill>/scripts/coverage.mjs <対象>/testcases` を実行する。
2. exit 1 なら、出力に出た未カバーの要素・形式エラー・問診の未記入・_flows の未登録を直し、もう一度実行する。**exit 0 になるまで繰り返す。**
3. exit 2 は入力ファイルの問題（inventory.json が無い、JSON が壊れているなど）。原因を直してから実行し直す。

## 工程 5: 完了報告

coverage.mjs が exit 0 を返したら、その出力をそのまま貼り、次を添えて報告する。

- 前提（工程 0 の回答）と、資料が無かった種類（そのぶん期待値が推測になっていること）
- risk: high の要素・フローとそのケース数
- findings の一覧（件数の多い順。不具合の候補）と、findings にまとめていない要確認
- 要注意（一部の画面だけ文脈が違う共通部品）と unreached の扱い
- excluded の件数と主な理由
- 手動追記した要素の一覧（スクリプトで拾えなかったもの。人の確認を勧める）
