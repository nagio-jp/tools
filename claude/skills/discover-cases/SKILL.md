# 機能 → 画面 → E2E テストケースの洗い出し

テスト設計の成果物として、対象の **機能一覧**、機能ごとの **画面**、機能ごとの **テストケース** を抜けなく洗い出す。目的は網羅したテストケースを作ることで、不具合を探すことではない。5 つの工程（0〜4）で進め、工程を飛ばしたり 1 回の応答でまとめて済ませたりしない。

- 対象: `$ARGUMENTS` の 1 つ目（省略時はカレントディレクトリ）。以下 `<対象>` と書く。2 つ目に URL があれば、起動中のアプリの URL として使う
- 成果物: `<対象>/testcases/` 配下のファイルだけ。人がレビューするのは最後に生成される `summary.md`
- スクリプト: このスキルのベースディレクトリの `scripts/`。以下では `<skill>/scripts/...` と書く。引数は絶対パスで渡す（シェルのカレントディレクトリがずれても壊れないように）
  - `sources.mjs`・`inventory.mjs`・`routes.mjs`・`features.mjs`・`coverage.mjs` は Node.js の標準モジュールだけで動く
  - `crawl.mjs` だけ Playwright が要る。対象プロジェクトに Playwright があれば `--project <対象>` で使える。無ければ `cd <skill>/scripts && npm install && npx playwright install chromium` を人に案内する（勝手にインストールしない）

## 絶対に守ること

- **このスキルは洗い出しだけを行う。** nagio などのテスト管理ツールや外部サービスへの登録・送信はしない。MCP のツールが使える環境でも呼ばない。
- **完了かどうかはあなたが判断しない。** coverage.mjs が exit 0 を返したときだけ完了と報告する。
- **スクリプトを書き換えない。** 判定基準が動くと網羅の意味がなくなる。スクリプトの不具合に気づいたら、回避したうえで人に報告する。
- **ケースは 1 件ずつ考えて書く。** スクリプトやテンプレートでケースを量産しない。
- **1 回の書き込みで扱うのは 1 機能（1 ファイル）だけ。** 1 回のコマンドやヒアドキュメントで複数機能のファイルを書かない。
- 「他も同様」「以下省略」「代表的なものだけ」のように省略しない。
- 人への質問は、選択肢から選ぶか「はい / いいえ」で答えられる形にする。選択式の質問ツール（AskUserQuestion など）があれば使う。自由記述を必須にしない。
- アプリの操作は巡回（crawl.mjs）と、人が許可した setup だけ。データを消す・送る操作を自分で実行しない。
- 途中で止まる場合は、どこまで終わったかを `<対象>/testcases/progress.md` に書いてから止まる。

## 工程 0: 問診

ケースの根拠にする資料と、ケースの前提を人と確かめる。人の負担を小さくするため、質問は選択式だけにする。

1. `node <skill>/scripts/sources.mjs <対象>` を実行する。資料の候補が種類ごとに番号付きで出て、`<対象>/testcases/sources.json` に保存される（フロントエンド / バックエンド / API 定義 / DB / 仕様・要件 / 既存のテスト / 認証 / デザイン）。
2. 候補のうち中身を見ないと判断できないもの（README、仕様らしき md、.env.example など）は読み、何が分かるかを一言ずつ添える。
3. 番号付きの一覧を短く示し、次の 4 問を **1 回で** 聞いて止まる。各問は選択肢で答えられるようにし、「分からない」も選べるようにする。

| # | 質問 | 選択肢 |
|---|------|--------|
| 1 | 見つかった資料はこれで合っていますか | はい / 違う（違う番号を教える） |
| 2 | ほかに参考にできる資料はありますか | なし / ある（パスか URL を貼る） |
| 3 | 入力した内容を保存・送信するサーバーはありますか | ある / ない / 分からない |
| 4 | ログインは必要ですか | 不要 / 必要 / 分からない |

   起動して巡回する対象（工程 2 の B）で URL が分からなければ、5 問目として「起動中のアプリの URL」を聞く（起動方法が分かるなら、選択肢として「`npm run dev` で起動してよい」を出す）。

4. 回答を sources.json の `answers` に書く。人が足した資料は、該当する種類の `found` に `{ "path": "<パスか URL>", "reason": "<何の資料か>", "source": "manual" }` で足す（どの種類にも当てはまらなければ `extra`）。

```json
"answers": {
  "sourcesConfirmed": true,
  "backend": "yes | no | unknown",
  "login": "no | yes | unknown",
  "appUrl": "http://localhost:3000",
  "auth": "テスト用アカウントや storageState のパス（login が yes のとき）"
}
```

「分からない」の扱い:

- `backend: unknown`: 保存・送信の結果（保存後の表示、送信失敗のエラー表示など）のケースは書く。期待値を決められないものには `question`（仕様の確認事項）を付ける
- `backend: no`: 保存・送信の結果のケースは書かない（画面の入力チェックなど、画面だけで完結するケースは書く）
- `login: unknown`: ログインが要りそうな画面は、巡回で開けたかで判断する。開けなければ人にログイン手段を聞く（工程 2）

### 資料の使い方

- 仕様・要件・デザイン: 機能一覧と期待値の根拠にする。ケースに `basis`（資料のパスと箇所）を書く
- API 定義・DB スキーマ: 機能（エンティティごとの作成・一覧・更新・削除）を洗い出す材料にする。必須・文字数・形式・一意性の制約を、入力チェック・境界値のケースの根拠にする
- 既存のテスト: 既にあるケースと重複させない。重複するものは書かず、progress.md に「既存の <ファイル> でカバー」と残す

## 工程 1: 機能の洗い出し

対象の機能一覧を作り、人に確認してもらう。画面の部品ではなく「利用者ができること」の単位で挙げる。

1. 機能の材料を集める。
   - 仕様・要件・README（工程 0 の資料）
   - API 定義・DB スキーマ（エンティティと操作）
   - 画面の一覧: 静的 HTML なら `node <skill>/scripts/inventory.mjs <対象>`、起動できるアプリなら `node <skill>/scripts/routes.mjs <対象>` を先に実行し、画面とタイトルを見る（棚卸しの詳細は工程 2）
2. `<対象>/testcases/features.json` を書く。

```json
{
  "features": [
    {
      "id": "auth.login",
      "group": "認証",
      "name": "ログイン",
      "description": "メールアドレスとパスワードでログインし、ダッシュボードを開く",
      "priority": "high",
      "screens": ["login.html"],
      "basis": ["docs/spec/auth.md 「ログイン」"]
    }
  ],
  "excludedScreens": []
}
```

   - `id` は `<グループの英字>.<機能の英字>`。`group` で機能をまとめる（例: 認証 / ダッシュボード / ユーザー管理 / 共通）
   - 次の観点で漏れなく挙げる
     - 画面ごとに、その画面でできること（表示する・入力して送る・絞り込む・並べ替える・切り替える）
     - 共通部品（ヘッダー・サイドバー・フッター・共通のメニュー）の操作は「共通ナビゲーション」「共通メニュー」などの機能にする
     - データ（エンティティ）ごとに、作成 → 一覧 → 詳細 → 更新 → 削除。画面にまたがる流れも 1 つの機能として扱ってよい
     - 認証・権限（ログイン・ログアウト・アカウント登録・パスワード再設定・権限による出し分け）
     - エラー画面・空の状態（404・0 件の一覧など）
   - `priority` は high / normal / low の案を付ける。迷ったら normal
   - `screens` は画面 ID（inventory / routes の画面の表記）。工程 2 で確定させるので、ここでは分かる範囲でよい
3. `node <skill>/scripts/features.mjs <対象>/testcases` で、機能一覧を「グループ → 機能」の木として番号付きで出す。
4. 木と優先度の案を示し、**ここで止まって人に確認する。** 質問は選択式にする:
   - 機能一覧はこれで合っていますか（はい / 直したい番号を教える / 足りない機能がある）
   - 優先度はこれでよいですか（はい / high にしたい番号 / low にしたい番号）
5. 回答を features.json に反映する。

## 工程 2: 画面の対応付け

画面と操作を機械的に棚卸しし、すべての画面・操作がどれかの機能に属するようにする。棚卸しは、機能の洗い出しの抜けを見つける材料でもある。

### A. 静的 HTML（ビルド不要で、.html をそのまま開けば動くもの）

`node <skill>/scripts/inventory.mjs <対象>` を実行する（工程 1 で実行済みなら不要）。出力の「HTML ファイル数」と「画面数」が一致することを確認する。

### B. 起動できるアプリ（React・Vue・Next.js など、静的 HTML でも JS で画面が変わるもの）

1. `node <skill>/scripts/routes.mjs <対象>` でソースからルートを拾う（Next.js の pages/・app/、Nuxt、SvelteKit、React Router・Vue Router など）。
2. 工程 0 の URL に対して巡回する: `node <skill>/scripts/crawl.mjs --base-url <URL> --out <対象>/testcases [--project <対象>]`
   - リンクをたどり、描画後の画面から操作できる要素を集める。ドロップダウン・タブは開いて中の要素も集める（開くだけで、送信・削除はしない）
   - `/users/123` のような URL は `/users/:id` として 1 画面にまとめる。一覧の行に並ぶ同じ操作は 1 要素にまとめる（`repeated` に件数）
   - ソースにあるのに巡回で開けなかったルートは `unreached`（理由付き）として載る
3. ログインが要る場合は、次のどちらかを人に用意してもらい、ログイン前とログイン後の両方を巡回する（`--session ログイン前 --session ログイン後=<対象>/testcases/auth.json`）。
   - storageState: 人に `npx playwright codegen --save-storage=<対象>/testcases/auth.json <URL>` でログインしてもらう
   - setup スクリプト: ログイン手順を書いた ES モジュール（`export default async (page, { baseUrl }) => { ... }`）。テスト用アカウントを人から聞いて、あなたが書いてよい。パスワードは環境変数から読む
4. データが無いと出ない画面・要素（空の一覧、行ごとの操作）は、setup スクリプトでデータを作ってから巡回する（`--session データあり=<setup>`）。作る操作は人の了承を得てから。
5. unreached の画面は、実在する URL を人に聞いて `--seed <URL>` で巡回し直すか、工程 2 の最後で対象外にする。

### 出力の見方と手動追記

- 共通部品: 半数以上の画面に同じ形で現れる要素は、擬似画面 `_layout` に 1 回だけ載る
- 画面ごとの違い: 共通部品でも、一部の画面だけ form の中にある・状態（現在地の強調など）が違うものは出力に出る。その画面を担当する機能のケースで、違いも確かめる
- 既知の UI ライブラリ（DataTables・Chart.js・地図など）を使う画面は、ライブラリが描く操作・表示（並べ替え・ページ送り・グラフの表示など）を手動追記する
- 各要素の ID は `<画面>#<種別>:<名前>`。種別: page / form / input / select / radio / checkbox / switch / button / toggle / tab / menuitem / action / link / external / state
- スクリプトで拾えないもの（JS で出るエラー表示・読み込み中・空の状態など）は、inventory.json の該当画面に `{ "id": "<画面>#<種別>:<名前>", "type": "<種別>", "description": "<何が起きるか>", "source": "manual" }` で追記する。再実行しても引き継がれる

### 足りないものをブラウザで確かめる（任意）

棚卸し・巡回・ソースの読み込みで拾いきれないものが残ったときだけ、Claude in Chrome（`mcp__claude-in-chrome__*` のブラウザ操作）で確かめるかを人に聞く。時間がかかるので、最初からは使わない。Claude in Chrome のツールが使えない環境では、この質問を出さない。問診（工程 0）で使うかどうかを先に聞くこともしない。

1. 聞くタイミング: 工程 2 の対応付けの後、または工程 4 の前に、次のような「足りないもの」が残ったとき。
   - unreached の画面（ログインやパラメータが要るなど）
   - ホバーや入れ子のメニューでしか出ない操作
   - onClick だけの要素など、巡回では拾えない操作
   - クローラーを使えない環境（Playwright が無いなど）で、JS で描かれる画面
2. 足りないものの一覧（画面・操作と件数）と、ブラウザで確かめた場合のおおよその手間（例: 画面 3 つで 5〜10 分）を示し、「Claude in Chrome で確かめますか（はい / いいえ）」と選択式で聞く。
3. いいえなら、その分は理由付きの対象外（`excludedScreens` / `excluded`）か、仕様の確認事項（`question`）にして先に進む。
4. はいなら、一覧に挙げた画面・操作だけを見る。それ以外の画面は開かない。データを消す・送る操作はしない。分かったことは inventory.json の該当画面に `source: "browser"` で追記する（形式は手動追記と同じ。再実行しても引き継がれる）。

### 機能との対応付け

1. 棚卸しの結果を見て、features.json の各機能の `screens` を確定させる。`_layout` は、共通部品を操作する機能（共通ナビゲーションなど）の `screens` に入れる。1 画面の中で表示を切り替えるアプリ（SPA で画面のほとんどが `_layout` にまとまる場合）は、各機能の `screens` に `_layout` を入れる。
2. どの機能にも属さない画面が出たら、機能を足すか、`excludedScreens` に理由付きで入れる（例: `{ "screen": "blank.html", "reason": "中身の無い見本のページ" }`）。unreached の画面も同じ扱い。
3. 機能を足した場合は、`features.mjs` の木を示して、足した機能だけ人に確認する（はい / 直す）。
4. `node <skill>/scripts/features.mjs <対象>/testcases` で、機能に属さない画面が 0 件になったことを確かめる。

## 工程 3: テストケース

機能ごとにテストケースを書く。

1. features.json の機能を 1 つずつ処理する。サブエージェントを使える環境なら機能ごとに任せてよい。その場合もサブエージェントには担当の機能、工程 0 の回答、この工程の内容を渡す。
2. 1 機能ごとに `<対象>/testcases/cases/<機能 ID>.json` を、1 回の書き込みで書く。

```json
{
  "feature": "auth.login",
  "cases": [
    {
      "id": "auth.login-001",
      "title": "登録済みのメールアドレスとパスワードでログインすると、ダッシュボードが開く",
      "perspective": "正常系",
      "screens": ["login.html", "index.html"],
      "covers": ["login.html#input:email", "login.html#input:password", "login.html#button:Login"],
      "preconditions": "ログイン画面を開いている。テスト用アカウントが登録済み",
      "steps": ["メールアドレスに登録済みのアドレスを入れる", "パスワードを入れる", "「Login」を押す"],
      "expected": "ダッシュボード（index.html）が開き、ユーザー名がヘッダーに表示される",
      "basis": "docs/spec/auth.md 「ログイン」"
    }
  ],
  "excluded": [
    { "element": "login.html#link:プライバシー->privacy.html", "reason": "プライバシーポリシーへの遷移は共通ナビゲーションで確認する" }
  ]
}
```

3. `perspective` は次のどれか（coverage.mjs が検査し、summary.md の列になる）。

| perspective | 何を確かめるか |
|-------------|----------------|
| 正常系 | 機能を正しく使ったとき、最後まで進み、結果が正しく表示される |
| 入力チェック | 必須の未入力、形式の誤り（メールアドレス・数値など）、前後の空白・全角文字 |
| 境界値 | 文字数・数値・件数の上限と下限の前後 |
| 画面遷移 | リンク・ボタン・戻る・再読み込み・URL 直接アクセスでの遷移と、遷移後の状態 |
| 表示 | 初期表示、状態ごとの表示（空・0 件・多数・読み込み中）、狭い画面幅、現在地の強調 |
| 権限・ログイン | 未ログインでのアクセス、権限ごとの出し分け、ログアウト後の扱い |
| データの流れ | 作成したデータが一覧・詳細に出る、更新が反映される、削除で消える、再読み込み後も残る |
| 異常系 | 保存・送信の失敗、二重送信、存在しないデータへのアクセス（`backend: no` なら書かない） |

4. priority による深さ:
   - `high`: 当てはまる観点をすべて書く。入力の組み合わせ（複数項目のエラーが同時に出るなど）も書く
   - `normal`: 当てはまる観点をすべて書く
   - `low`: 正常系と表示だけ書く。省いた要素は `excluded` に理由付きで書く
   - 当てはまらない観点は書かない（例: 入力欄の無い機能の入力チェック）
5. 期待値:
   - 資料に根拠があれば、それに沿って書き、`basis` に資料のパスと箇所を書く
   - 資料が無ければ、画面の現状の挙動から書く
   - どちらでも決められない（仕様が分からない）ものは、分かる範囲で期待値を書き、`question` に「何が決まっていないか」を 1 文で書く。これが summary.md の「仕様の確認事項」になる
   - 「正しく表示される」のような曖昧な期待値は書かない。画面を見ずに第三者が実施・判定できる具体さで書く
6. `covers` には、そのケースで操作・確認する要素の ID を inventory.json からそのまま写す（推測で書かない）。`screens` には、そのケースで通る画面を書く。機能の `screens` に無い画面を通るなら、features.json の `screens` に足す（`_layout` は足さなくてよい）。
7. その機能の画面にある要素で、どのケースでも触れないものは `excluded` に理由付きで書く（別の機能で確認する、など）。
8. 1 機能を書き終えるたびに `<対象>/testcases/progress.md` に完了した機能を追記する。

## 工程 4: 抜けの確認

1. `node <skill>/scripts/coverage.mjs <対象>/testcases` を実行する。次を判定する。
   - 問診の回答（`sourcesConfirmed`・`backend`・`login`）が埋まっている
   - 全機能にケースが 1 件以上ある
   - 全画面が、どれかの機能に属するか、理由付きで対象外になっている
   - 全要素が、どれかのケースの `covers` に入るか、理由付きで `excluded` に入っている
   - ケースの形式（perspective が決められた値か、covers の ID が実在するか など）
2. exit 1 なら、出力に出た抜けや形式エラーを直し、もう一度実行する。**exit 0 になるまで繰り返す。**
3. exit 2 は入力ファイルの問題（features.json が無い、JSON が壊れているなど）。原因を直してから実行し直す。
4. coverage.mjs は `<対象>/testcases/summary.md` を書き出す（機能グループ → 機能 → 画面 → 観点別のケース数、仕様の確認事項、対象外の画面）。

## 完了報告

coverage.mjs が exit 0 を返したら、その出力をそのまま貼り、次を添えて報告する。

- `summary.md` のパス（人がレビューするのはこのファイル）
- 機能の数・ケースの数、priority: high の機能とそのケース数
